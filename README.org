* CharmVZ

A batch alternative to the Projections visualization tool for analyzing Charm++ trace files. Instead of providing a GUI, CharmVZ converts a trace directory into a set of Parquet tables that can be queried from Python, R, Julia, DuckDB, or anything else that reads Parquet.

The repository also contains [[file:charmvz-viz/][charmvz-viz]], a Python package that reads those tables and reproduces the Projections visualizations.

** Status

Working. The pipeline builds, runs end to end, and processes the project's reference traces correctly: a 4-PE ChaNGa trace (6.6M executions) in about 25 s, and the two 80-PE LeanMD traces.

Two caveats worth knowing before relying on it:

- The trace format is pinned to Projections version *11.0*. The STS parser rejects any other ~VERSION~ outright rather than guessing.
- Aggregate output has not yet been cross-validated against Projections itself. The reconstruction follows the documented rules and the derived counts are internally consistent, but a side-by-side comparison against the Java tool is still outstanding.

** Overview

CharmVZ bridges Charm++ performance tracing and modern data analysis. [[https://github.com/charmplusplus/projections][Projections]] provides an interactive GUI; CharmVZ targets programmatic analysis, scripted comparison across runs, and custom visualization, by turning the trace into a normalized relational schema.

*** Key features

- *Streaming*: logs are parsed line by line and flushed in row groups, so a multi-gigabyte trace never lands in memory at once
- *Transparent decompression*: plain ~.log~ and gzipped ~.log.gz~ are read the same way, and a single trace directory may mix both
- *Normalized schema*: 13 tables with explicit keys, rather than one flat event dump
- *Precomputed derived columns*: durations, queue waits and PAPI deltas are stored, not recomputed downstream
- *Compressed output*: ZSTD by default, measured 2.54x smaller than Parquet's uncompressed default for about 7% more wall time
- *Application semantics*: user events, user statistics and memory samples are materialized, and application-declared timesteps become a first-class dimension
- *Explicit incompleteness*: a record whose end was never logged is written with NULL end fields and counted, never dropped silently or paired with an invented start

** Installation

*** Prerequisites

- C++20 compatible compiler (GCC 10+ or Clang 12+)
- [[https://mesonbuild.com/][Meson]] build system and [[https://ninja-build.org/][Ninja]] backend

*** Dependencies

All but one are *system dependencies* that must be installed beforehand; Meson locates them with ~dependency()~ and does not fetch them.

- *Apache Arrow* and *Parquet* (C++): the output format
- *spdlog* (>= 1.15.3): logging
- *CLI11* (>= 2.5.0): command-line parsing
- *zlib*: gzip support for compressed logs
- *Catch2* (>= 3.10.0): tests only, and optional. The test targets are guarded by ~if catch2_dep.found()~, so a build without it still succeeds and simply skips them

~zstr~ is the one vendored dependency: a git submodule at ~subprojects/zstr~, consumed as a CMake subproject.

On macOS with Homebrew:

#+begin_src bash
brew install meson ninja apache-arrow spdlog cli11 catch2
#+end_src

*** Build instructions

#+begin_src bash

*** Building on the Kabré cluster

Worth its own section because the login node misrepresents the machine you
have to run on, in three separate ways.

| | Login (~login-*.cnca~) | Compute (~kura-*.cnca~) |
|---------+------------------------+-------------------------|
| OS | AlmaLinux 9.7 | AlmaLinux 8.10 |
| glibc | 2.34 | 2.28 |
| System ~g++~ | 11.5 | 8.5 |
| ~gcc/13.4.0~ module | works | will not start |
| GNU ~time~ | present | absent |

Binaries have to run on the compute nodes, so glibc 2.28 is the target. The
~gcc~ modules are built for the login image and abort with missing
~GLIBC_2.32~ symbols on a compute node, and the compute nodes' own ~g++~ 8.5
predates the C++20 this project needs. Neither system compiler is usable.

Nor is Arrow available anywhere on the cluster, in any form. The route that
works is a user-space conda environment providing Arrow, Parquet, spdlog,
CLI11, meson and ninja. Its libraries need at most ~GLIBC_2.17~, so they load
on the compute nodes without complaint.

One gap remains. The conda toolchain is ~gcc~ 16, whose ~libstdc++~ inlines a
read of ~__libc_single_threaded~ into anything using ~shared_ptr~. That object
arrived in glibc 2.32 and does not exist in 2.28, so every such translation
unit fails to link. Note that conda's own ~sysroot_linux-64~ does not save you
here: the package is labelled 2.34 but ships a glibc 2.28 ~libc.so.6~.

Supplying the symbol resolves it, and costs nothing the platform would not
already pay, since a ~libstdc++~ built against 2.28 uses the atomic refcount
path regardless:

#+begin_src cpp
// glibc228_compat.cpp
extern "C" char __libc_single_threaded = 0;
#+end_src

#+begin_src bash
ENV=/path/to/conda/env
export PATH="$ENV/bin:$PATH" PKG_CONFIG_PATH="$ENV/lib/pkgconfig"
export LD_LIBRARY_PATH="$ENV/lib:$LD_LIBRARY_PATH"
export CC="$ENV/bin/x86_64-conda-linux-gnu-cc" CXX="$ENV/bin/x86_64-conda-linux-gnu-c++"
$CXX -O2 -fPIC -c glibc228_compat.cpp -o glibc228_compat.o
export LDFLAGS="$PWD/glibc228_compat.o"
meson setup builddir-kabre --buildtype=release && meson compile -C builddir-kabre
#+end_src

Build and test on a compute node, never the login node: the login nodes are
limited, and a build that succeeds there may not even start where it has to
run. The test suite passes under this configuration against Arrow 25.0.0.

** Usage

*** Command line

#+begin_src bash
./builddir-rel/charmvz -l <trace_dir> -o <output_dir> [-s <step_event_name>]
#+end_src

| Option | Required | Description |
|--------+----------+-------------|
| ~-l~, ~--logs~ | yes | Directory holding the ~.sts~, ~.projrc~ and per-PE log files |
| ~-o~, ~--output~ | yes | Directory for the Parquet output; created if absent |
| ~-s~, ~--step-event~ | no | Name of the registered user event that delimits a timestep (default ~SimulationStep~) |

The whole trace directory is passed at once, not a single file: CharmVZ discovers the ~.sts~, the ~.projrc~ and every per-PE log inside it. Only files named ~<pgm>.<pe>.log~ or ~<pgm>.<pe>.log.gz~ are read as logs; any other ~.gz~ in the directory, such as an archive of the trace itself, is ignored with a warning. A missing ~.sts~ aborts the conversion. A missing ~.projrc~ only produces a warning, but disables the cross-PE derivations described under [[*Timestamps and the clock reference][Timestamps and the clock reference]].

*** Input files

Standard Charm++ Projections output, produced by building with ~-tracemode projections~ and running with ~+traceroot~:

- ~<pgm>.sts~ -- symbol table: chare, entry-method, message and user-event names; PE count; PAPI counter names
- ~<pgm>.projrc~ -- global start and end time; its presence is what makes cross-PE time differences meaningful
- ~<pgm>.<pe>.log~ or ~<pgm>.<pe>.log.gz~ -- one time-ordered event log per PE

#+begin_src bash
./charmrun +p4 ./myapp +traceroot traces/
#+end_src

A Charm++ built with ~-DZLIB=1~ writes the logs gzipped. Both forms are read transparently, and mixing them in one directory is fine.

*** Output tables

| Table | Primary key | Contents |
|-------+-------------+----------|
| ~processing_element.parquet~ | ~pe_id~ | One row per PE log file |
| ~chare_collection.parquet~ | ~collection_id~ | Chare types, with their ~ndims~ |
| ~entry_method.parquet~ | ~ep_id~ | Entry methods and their owning collection |
| ~message_type.parquet~ | ~msg_idx~ | Declared message sizes from the STS |
| ~chare_instance.parquet~ | ~instance_id~ | Chare elements; natural key ~(collection_id, index_0..5)~ |
| ~execution.parquet~ | ~(pe_id, event)~ | Paired BEGIN/END_PROCESSING, with PAPI counters |
| ~message.parquet~ | ~message_id~ | Sends linked to their receiving execution |
| ~idle_interval.parquet~ | ~(pe_id, start_time_us)~ | Paired BEGIN/END_IDLE |
| ~migration_episode.parquet~ | ~migration_id~ | PE transitions of chare-array elements |
| ~user_event.parquet~ | -- | Application-emitted trace events, point and bracketed |
| ~user_stat.parquet~ | -- | Samples of statistics registered with ~traceRegisterUserStat()~ |
| ~memory_sample.parquet~ | -- | Heap-usage samples from ~traceMemoryUsage()~ |
| ~simulation_step.parquet~ | ~(step_id, pe_id)~ | Application timesteps |

Every table is written on every run, even when empty, so an empty file means "nothing of this kind was traced" rather than "the pipeline did not run". Column names and types are defined in [[file:src/schema.cpp][src/schema.cpp]].

Fields the trace did not observe are NULL rather than a sentinel: an execution whose ~END_PROCESSING~ never appears has NULL end fields, a message whose receiver cannot be identified has NULL receiver fields, and a receive time the runtime recorded as ~-1~ is NULL. Each such case is also counted and reported in the log output.

*** Timestamps and the clock reference

All timestamps are integer microseconds, stored exactly as the logs hold them. When the runtime computes a global start offset, it has already subtracted it from every record before writing the logs, so CharmVZ never subtracts it again; the value is kept as ~processing_element.global_start_us~.

The offset is an origin shift, not a clock synchronization: per-PE clock skew is not recorded anywhere in the trace. Differences between timestamps from two PEs are therefore only computed when a ~.projrc~ with ~RC_GLOBAL_START_TIME~ is present (a zero offset counts). Without one:

- ~message.enqueue_to_exec_us~ and ~message.end_to_end_us~ are NULL, except for messages a PE sent to itself
- ~migration_episode.parquet~ is empty
- ~processing_element.global_start_us~ and ~aligned_begin_us~ are NULL

The one non-microsecond time column is ~user_stat.user_time_s~, which holds the application-supplied value from ~updateStatPair()~ in whatever unit the application used.

*** Timesteps

The Charm++ runtime has no notion of a timestep, so ~simulation_step.parquet~ is populated only when the application declares its own boundaries. To make that happen, register a user event and bracket each step with it, passing the step index as the ~nestedID~ argument:

#+begin_src cpp
// once, at startup
int stepUE = traceRegisterUserEvent("SimulationStep");

// around each timestep
beginUserBracketEvent(stepUE, step);
// ... the timestep ...
endUserBracketEvent(stepUE, step);
#+end_src

Pass a different name with ~-s~ if you register one. If no matching event is found, CharmVZ logs a note and writes an empty ~simulation_step.parquet~ -- an uninstrumented trace is a normal input, not an error.

The table has one row per ~(step_id, pe_id)~. Attribute an execution to the step whose interval *on its own PE* contains it: PEs cross a boundary microseconds apart, so the denormalized ~global_start_time_us~ / ~global_end_time_us~ columns overlap between adjacent steps and are for display rather than attribution.

** Analysis examples

*** Python with polars

#+begin_src python
import polars as pl

execution = pl.scan_parquet("out/execution.parquet")
entry_method = pl.scan_parquet("out/entry_method.parquet")

# Time spent per entry method, named rather than numbered
by_ep = (
    execution.group_by("ep_id")
    .agg(
        pl.col("wall_duration_us").sum().alias("total_us"),
        pl.col("wall_duration_us").mean().alias("mean_us"),
        pl.len().alias("calls"),
    )
    .join(entry_method.select("ep_id", "name"), on="ep_id")
    .sort("total_us", descending=True)
)
print(by_ep.collect().head(10))
#+end_src

*** Python with pandas

#+begin_src python
import pandas as pd

df = pd.read_parquet("out/execution.parquet")

# Load imbalance: busy time per PE
per_pe = df.groupby("pe_id")["wall_duration_us"].sum()
print("max/mean =", per_pe.max() / per_pe.mean())

df["wall_duration_us"].hist(bins=50)
#+end_src

*** R with arrow and dplyr

#+begin_src r
library(arrow)
library(dplyr)

execution <- read_parquet("out/execution.parquet")

execution %>%
  group_by(pe_id) %>%
  summarise(
    total_us  = sum(wall_duration_us),
    events    = n(),
    mean_us   = mean(wall_duration_us)
  )
#+end_src

*** PAPI counters

When the trace was collected with PAPI active, ~execution.parquet~ carries six fixed counter columns per direction (~papi_begin_0..5~, ~papi_end_0..5~, ~papi_delta_0..5~). The columns stay numerically indexed; the counter *names* live in the file's Arrow schema metadata, so consumers never have to introspect the schema before querying:

#+begin_src python
import pyarrow.parquet as pq

meta = pq.read_schema("out/execution.parquet").metadata
print(meta[b"papi_event_0"])   # e.g. b'PAPI_L2_TCM'
#+end_src

** charmvz-viz

The [[file:charmvz-viz/][charmvz-viz]] subdirectory is a separate Python package (~charmvz_vis~) that reads the output directory and provides analysis and plotting APIs modelled on the Projections views -- time profile, usage profile, entry-point profile, histograms, per-PE communication, and extrema analysis.

#+begin_src python
import charmvz_vis as cv

ds = cv.TraceDataset("out/")
cv.time_profile(ds)
cv.usage_profile(ds)
#+end_src

See [[file:charmvz-viz/README.org][charmvz-viz/README.org]] for setup and the full API.

** Architecture

A four-stage pipeline, orchestrated in ~src/main.cpp~. Logs are never read into memory in full.

| Stage | Work |
|-------+------|
| 1 | Parse ~.sts~ and ~.projrc~; write the metadata tables; resolve the step-boundary event |
| 2 | Stream each PE log; write Execution, IdleInterval, ChareInstance, UserEvent, UserStat and MemorySample rows; retain only the keys needed to link records across PEs |
| 3 | Cross-PE reconstruction: ProcessingElement rows, message linkage, migrations |
| 4 | Fold per-PE step brackets into SimulationStep rows |

| File | Role |
|------+------|
| ~src/main.cpp~ | CLI, trace discovery, stage orchestration |
| ~src/sts_parser.*~, ~src/rc_parser.*~ | Stage 1 parsers |
| ~src/metadata_tables.*~ | Stage 1 output tables |
| ~src/log_parser.*~ | Stage 2 streaming parser |
| ~src/reconstruction.*~ | Stages 3 and 4 |
| ~src/builders.*~ | Arrow column builders that flush in row groups |
| ~src/schema.*~ | The 13 Arrow schemas |
| ~src/parquet_writer.*~ | Parquet output (ZSTD, schema metadata preserved) |
| ~src/utils/log_entry.*~ | Record type codes and the parsed record struct |

All pipeline code is built into the ~charmvz_lib~ library; the ~charmvz~ executable is only ~src/main.cpp~ linked against it, which lets the tests drive the pipeline functions directly.

Stage 2 is where the volume is. Arrow column builders flush a row group every 100,000 rows, so memory for row-level output stays flat regardless of trace size. What Stages 3 and 4 need -- one entry per send, per receive and per chare-array execution -- is kept in memory until all logs are read, so that part grows with the number of messages rather than staying constant.

Some details that are easy to get wrong and are handled deliberately:

- A chare array writes exactly ~ndims~ index values, not a fixed four. Reading four consumes an unrelated field as an index for 3-D arrays and under-reads 6-D ones.
- Migrations are derived from PE transitions between consecutive executions of an element. Pack/unpack events are message serialization, not migration, and ~CkLocMgr::emigrate()~ emits no tracing at all -- so a migration has no directly measurable cost in a trace.
- Message linkage matches on ~(src_pe, event)~, never on the event serial alone, which is only unique per PE, and additionally requires the receiver to run the entry method the message was created for. Several receivers on one PE are folded into one delivery only when they are resumes of a threaded entry method; any other repetition is written without receiver fields and counted rather than resolved by guessing.
- A broadcast is one row with no destination; a multicast is one row per listed destination.
- Bracketed user events carry a ~pe~ field that is always 0, so they are attributed to the PE that owns the log file. Every table takes its PE from the log file name for the same reason.
- ~MEMORY_USAGE_CURRENT~ writes its byte count before its timestamp, the reverse of every other record, and ~USER_STAT~ writes the application's time as a raw float.

** Testing

#+begin_src bash
meson test -C builddir-rel
#+end_src

Catch2 suites live in ~tests/~, one file per unit: ~test_sts_parser~, ~test_parquet_writer~, ~test_log_parser~, ~test_chare_index~, ~test_migration~, ~test_user_stat~ and ~test_reconstruction~. Most write a small synthetic trace with the shared fixture in ~tests/trace_fixture.h~, run the pipeline functions, and read the Parquet output back. To add a suite, create ~tests/test_<unit>.cpp~ and append the unit name to the ~foreach~ list in ~meson.build~.

The Python package has its own suite:

#+begin_src bash
cd charmvz-viz && pytest
#+end_src

New tests are expected to be *mutation-checked*: revert the behaviour a test guards and confirm the test fails. A test that still passes against the broken version is not testing what it claims to.
